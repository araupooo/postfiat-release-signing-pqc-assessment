Post-Quantum Release-Signing Assessment for PFTL

Measured signing costs for a hybrid Ed25519 + ML-DSA-65 release scheme against SLH-DSA, with negative tests, a key-rotation drill, and a mapping to the release and signing code in postfiatd (pinned commit 0085a1ff885d6a446369cf73a4430f75af22be55).

Headline finding. The hybrid scheme wins on every measured axis on this host. Hybrid verification costs 190.366 µs (median) against 710.776 µs for SLH-DSA-SHA2-128s (liboqs) — about 3.73× faster — and a hybrid signature is 3,373 bytes against 7,856 bytes for SLH-DSA-128s and 17,088 bytes for SLH-DSA-128f. Signing is the starkest gap: hybrid signing costs 139.669 µs while SLH-DSA-128s signing costs 692670.570 µs (liboqs), about 4959.4× more, because the small-signature SLH-DSA parameter sets trade signing time for size. Recommendation: sign releases with hybrid Ed25519 + ML-DSA-65 now, keep SLH-DSA-128s as the hash-based fallback in case lattice schemes fail.

Call-site mapping

postfiatd has no release-artifact signing: docs/RELEASE.md describes a version-string + Docker-tag + GitHub Release process with no artifact signatures or checksums. The closest real code is the validator manifest system — src/xrpld/app/misc/Manifest.h:66-77 (ephemeral-key compromise response and revocation) and src/xrpld/app/misc/detail/Manifest.cpp:196 (Manifest::verify) — and transaction/validation signing in src/libxrpl/protocol/SecretKey.cpp:230-276 (signDigest secp256k1, sign Ed25519) and src/libxrpl/protocol/STValidation.cpp:131-141 (validation verifyDigest). Reproduction

bash run_all.sh

Regenerates every derived output offline from the vendored results JSON (results/signing_*.json), rebuilds this page, and verifies digests. Expected: exit 0, byte-identical outputs. See REPRODUCTION.md for the exact command and recorded result. To re-run the signing measurements themselves (not part of the offline reproduction — timings vary run to run), see harness/build_signing.sh and harness/run_signing.sh.

Limitations

  • Timings are for this host and toolchain only (shared virtual CPU, gcc 13.3.0, -O2). They do not transfer to release or validator hardware; the ratios between schemes on one host are the portable part. SLH-DSA-128s signing is slow in both reference implementations here (hundreds of milliseconds to over a second); optimized implementations would be faster, but the ordering (128f much faster to sign than 128s, hybrid fastest) is structural.
  • liboqs uses its optimized x86_64 path; PQClean clean is portable C. A production deployment would use optimized code for both schemes; the PQClean numbers are a conservative upper bound.
  • OpenSSL 3.5 was not measured (see the claim index): the system OpenSSL is 3.0.13, which has no native ML-DSA or SLH-DSA.
  • The test keys are ephemeral, generated fresh on every run, and never written to disk. The manifest format is a proposal for the assessment, not a deployed format.
  • No release was signed or published for postfiatd; no ledger was compiled or run locally.
